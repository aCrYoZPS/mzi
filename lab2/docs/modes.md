## 1. Общие соглашения

| | |
|---|---|
| Блок | 16 байт (128 бит) |
| Байты ↔ число | little-endian: `u128::from_le_bytes` / `to_le_bytes` (уже есть `BelT::block_from`) |
| `F(·)` | `BelT::encrypt_block` — зашифрование блока (п. 6.1.3) |
| `F⁻¹(·)` | `BelT::decrypt_block` — расшифрование блока (п. 6.1.4) |
| Ключ | `Key<8>` = 8 слов `u32`, слово `i` — байты `4i..4i+4` ключа в little-endian |
| `Left_r(u)` | первые `r` байт блока `u` |
| `⟨1⟩₁₂₈` | единица как 128-битное число, т.е. `wrapping_add(1)` над `u128` |

`Left_r` — это **младшие** биты `u128`, а не старшие: блок собирается через
`from_le_bytes`, а стандарт нумерует байты с начала строки. Подтверждается
примерами из п. 5 самого стандарта: `ShLo⁸(B194BAC8) = 94BAC800` (сдвиг «вниз»
выбрасывает первый байт), `ShHi⁸(B194BAC8) = 00B194BA`. В коде это либо первые
`r` байт `to_le_bytes()`, либо маска `u128::MAX >> (128 - 8r)`; парный
`Right_{128-r}` — сдвиг вправо на `8r`.

Ключ в `common::cli::parse_key` собирается через `u32::from_le_bytes`, поэтому
hex-ключ из стандарта вводится в CLI как есть, байт за байтом:
`E9DEE72C8F0C0FA62DDB49F46F73964706075316ED247A3739CBA38303A98BF6`.

**В обоих гамма-режимах (`CTR`, `CFM`) `F⁻¹` не используется вообще** — и при
зашифровании, и при расшифровании вызывается только `encrypt_block`.

### Формат шифртекста (наша договорённость, не стандарт)

Стандарт считает синхропосылку `S` внешним параметром. В проекте (как в lab1) она
генерируется случайно при зашифровании и кладётся открытым текстом первым блоком:

```
шифртекст = S (16 байт) ‖ гамма-поток (|X| байт)
```

Это уже заложено в `lab2/src/main.rs`: для `CTR` и `CFM` назначен
`cli::at_least(BLOCK_SIZE)`, который перед расшифрованием проверяет `len ≥ 16`.
Сам CLI про режимы ничего не знает — каждый режим отдаёт ему две проверки
(`checking_plaintext`, `checking_ciphertext`), а CLI только зовёт их и
подписывает ошибку именем режима. `belt-cbc` кладёт `S` так же, первым блоком,
поэтому его проверка шифртекста — `at_least(2 * BLOCK_SIZE)` (синхропосылка плюс
хотя бы один блок).
Дополнения (паддинга) в этих режимах нет, длина сохраняется:
`|Y| = 16 + |X|`. Ограничения снизу на `|X|` нет (п. 6.4.1, 6.5.1: только
`|Xₙ| ≤ 128` бит), последний неполный блок гаммируется по фактической длине.

Требование к `S`: **не должна повторяться при одном и том же ключе**. Для `CTR`
повтор катастрофичен (XOR двух шифртекстов = XOR открытых текстов), для `CFM` тоже
нежелателен. 128 случайных бит на сообщение это обеспечивают.

Генерация (`rand 0.10` уже в `lab2/Cargo.toml`, как в lab1):

```rust
use rand::RngExt;

let sync: u128 = rand::rng().random();
```

## 3. Режим простой замены, п. 6.2 (`belt-ecb`)

### Кража шифртекста вместо дополнения нулями

Первая версия `encrypt_ecb` добивала нулями до кратности 16 и клала в конец байт
с числом добитых байт (`|Y| = |X| + pad + 1`) — обратимо, но не по стандарту.

Стандарт (п. 6.2.1–6.2.3): `|X| ≥ 128` бит, дополнения нулями нет, длина
сохраняется (`|Y| = |X|`), неполный последний блок обрабатывается **кражей
шифртекста** (ciphertext stealing) — недостающие биты берутся из предыдущего
блока шифртекста:

```
Если |Xₙ| = 128:   Yᵢ ← F(Xᵢ),  i = 1..n
Иначе (0 < r = |Xₙ| < 128):
    Yᵢ      ← F(Xᵢ),  i = 1..n-2
    Y*      ← F(X_{n-1})
    Yₙ      ← Left_r(Y*)
    Y_{n-1} ← F( Xₙ ‖ (последние 16-r байт Y*) )
```

Хорошо видно на векторах: в А.7 (`|X| = 376` бит) последние 15 байт шифртекста —
это первые 15 байт того блока, который в А.6 (`|X| = 384`) стоит вторым.
Расшифрование (п. 6.2.4) — тот же алгоритм с `F⁻¹`, перестановка симметрична.

### Реализация CTS (проверена на А.6–А.9)

```rust
fn apply_ecb(mut bytes: Vec<u8>, key: &Key<8>, encrypt: bool) -> Vec<u8> {
    let full = bytes.len() / BLOCK_SIZE;   // число полных блоков
    let rest = bytes.len() % BLOCK_SIZE;   // |X_n|, если последний блок неполный

    let apply = |n: u128| {
        if encrypt { Self::encrypt_block(n, key) } else { Self::decrypt_block(n, key) }
    };

    for i in 0..full {
        let processed = apply(Self::block_from(&bytes[i * BLOCK_SIZE..][..BLOCK_SIZE]));
        bytes[i * BLOCK_SIZE..][..BLOCK_SIZE].copy_from_slice(&processed.to_le_bytes());
    }

    if rest != 0 {
        let last = (full - 1) * BLOCK_SIZE;         // блок n-1
        for j in 0..rest {
            bytes.swap(last + j, last + BLOCK_SIZE + j);   // кража шифртекста
        }
        let processed = apply(Self::block_from(&bytes[last..][..BLOCK_SIZE]));
        bytes[last..][..BLOCK_SIZE].copy_from_slice(&processed.to_le_bytes());
    }

    return bytes;
}
```

`encrypt_ecb` / `decrypt_ecb` — это `apply_ecb(bytes, key, true/false)`.

### Что это потребовало от CLI

* Проверки шифртекста больше не живут в `common`: `CipherMode` хранит
  `plaintext_check` и `ciphertext_check` — обычные замыкания
  `Fn(&[u8]) -> Result<(), String>`, которые режим задаёт сам и в которые
  зашивает свой размер блока. `common::cli::at_least(n)` — единственная общая
  заготовка, всё остальное (например, «блоки плюс байт паддинга» у ГОСТа)
  описывается в своей лабе.
* `|X| ≥ 16` требуется уже при зашифровании, поэтому CLI зовёт
  `plaintext_check` перед `encrypt`, симметрично `ciphertext_check` перед
  `decrypt`.

## 4. Режим сцепления блоков, п. 6.3 (`belt-cbc`)

В исходное задание не входил, но сделан и сверен с А.10–А.13.

Формулы из PDF не извлекаются, поэтому шаги п. 6.3.3 и 6.3.4 восстанавливались
по обрывкам текста и проверялись векторами. Ниже `n` — число блоков,
`r = |Xₙ|`, `W` — промежуточное значение, которое в стандарте живёт в `Y_{n-1}`
до перезаписи.

Зашифрование (п. 6.3.3):

```
Y₀ ← S
если |Xₙ| = 128:   Yᵢ ← F(Xᵢ ⊕ Y_{i-1}),  i = 1..n
иначе (0 < r < 128):
    Yᵢ      ← F(Xᵢ ⊕ Y_{i-1}),  i = 1..n-2
    W       ← F(X_{n-1} ⊕ Y_{n-2})
    Yₙ      ← Left_r(W)
    Y_{n-1} ← F((Xₙ ‖ 0…0) ⊕ W)
```

Последняя строка — обычный шаг сцепления, только предыдущим блоком шифртекста
служит `W`, а неполный `Xₙ` дополнен нулями до 16 байт. На векторах это видно
прямо: в А.11 (36 байт) последние 4 байта шифртекста — это первые 4 байта того
блока, который в А.10 (48 байт) стоит вторым.

Расшифрование (п. 6.3.4) — то же в обратную сторону:

```
Xᵢ      ← F⁻¹(Yᵢ) ⊕ Y_{i-1},  i = 1..n-2
W'      ← F⁻¹(Y_{n-1}) ⊕ (Yₙ ‖ 0…0)
Xₙ      ← Left_r(W')
W       ← Yₙ ‖ Right_{128-r}(W')
X_{n-1} ← F⁻¹(W) ⊕ Y_{n-2}
```

Формат шифртекста — как у гамма-режимов, `S ‖ тело`, поэтому проверка
шифртекста здесь `at_least(2 * BLOCK_SIZE)`: синхропосылка плюс хотя бы один
блок. Изначально `S` дописывалась в конец, и `decrypt_cbc` брала её по
`len - BLOCK_SIZE` вообще без проверки длины.

Требование `|X| ≥ 16` такое же, как у ECB: красть шифртекст не у кого. В
`apply_ecb` и `apply_cbc` на это стоит `assert!`, иначе `full - 1` на коротком
входе уходит в переполнение.

### Найденная ошибка

Цикл сцепления выходил по `idx == full - 1`, а дальше стояло
`if rest == 0 { return result; }`. То есть **при длине, кратной 16, последний
блок молча терялся**: А.10 давала 32 байта вместо 48, round-trip этого не
замечал, потому что расшифрование теряло блок симметрично. Ветка с кражей
шифртекста при этом была верна — А.11 сошлась сразу.

Правильный признак: в цепочке `full` блоков, если хвоста нет, и `full - 1`,
если есть:

```rust
let chained = if rest == 0 { full } else { full - 1 };
for block in bytes.chunks_exact(BLOCK_SIZE).take(chained) { ... }
```

## 5. Режим счётчика, п. 6.5 (`CTR`)

```
s ← F(S)
для i = 1..n:
    s  ← s + ⟨1⟩₁₂₈          (mod 2¹²⁸, счётчик — LE-число)
    Yᵢ ← Xᵢ ⊕ Left_{|Xᵢ|}(F(s))
```

Расшифрование (п. 6.5.4) — **та же процедура**. Важные детали: счётчик
инкрементируется *до* первого гаммирования (первая гамма — `F(F(S) + 1)`, а не
`F(F(S))`), и шифруется значение счётчика, а не предыдущая гамма.

```rust
fn apply_ctr(bytes: &[u8], key: &Key<8>, sync: u128) -> Vec<u8> {
    let mut counter = Self::encrypt_block(sync, key);
    let mut result = Vec::with_capacity(bytes.len());

    for block in bytes.chunks(BLOCK_SIZE) {
        counter = counter.wrapping_add(1);
        let gamma = Self::encrypt_block(counter, key).to_le_bytes();
        result.extend(block.iter().zip(gamma).map(|(byte, g)| byte ^ g));
    }

    return result;
}

pub fn encrypt_ctr(plain_bytes: Vec<u8>, key: &Key<8>) -> Vec<u8> {
    let sync: u128 = rand::rng().random();

    let mut result = Vec::with_capacity(BLOCK_SIZE + plain_bytes.len());
    result.extend_from_slice(&sync.to_le_bytes());
    result.extend_from_slice(&Self::apply_ctr(&plain_bytes, key, sync));

    return result;
}

pub fn decrypt_ctr(encrypted_bytes: Vec<u8>, key: &Key<8>) -> Vec<u8> {
    // len >= BLOCK_SIZE гарантирует cli::check_sync_prefix
    let (sync, body) = encrypted_bytes.split_at(BLOCK_SIZE);

    return Self::apply_ctr(body, key, Self::block_from(sync));
}
```

Свойства для отчёта: длина сохраняется; блоки независимы (распараллеливание,
произвольный доступ к блокам); одиночная ошибка в бите шифртекста портит ровно тот
же бит открытого текста — размножения ошибок нет; одинаковые блоки открытого
текста дают разные блоки шифртекста.

## 6. Режим гаммирования с обратной связью, п. 6.4 (`CFM`)

Регистр обратной связи — предыдущий блок **шифртекста**:

```
Y₀ ← S
Зашифрование:   Yᵢ ← Xᵢ ⊕ Left_{|Xᵢ|}(F(Y_{i-1}))
Расшифрование:  Xᵢ ← Yᵢ ⊕ Left_{|Yᵢ|}(F(Y_{i-1}))
```

Единственная разница между направлениями — что уходит в регистр: при
зашифровании результат XOR, при расшифровании входной блок. Неполный блок всегда
последний, регистр после него уже не нужен.

```rust
fn apply_cfm(bytes: &[u8], key: &Key<8>, sync: u128, encrypt: bool) -> Vec<u8> {
    let mut feedback = sync;
    let mut result = Vec::with_capacity(bytes.len());

    for block in bytes.chunks(BLOCK_SIZE) {
        let gamma = Self::encrypt_block(feedback, key).to_le_bytes();
        let processed: Vec<u8> = block.iter().zip(gamma).map(|(byte, g)| byte ^ g).collect();

        let cipher_block = if encrypt { &processed[..] } else { block };
        if cipher_block.len() == BLOCK_SIZE {
            feedback = Self::block_from(cipher_block);
        }

        result.extend_from_slice(&processed);
    }

    return result;
}
```

Обвязка `encrypt_cfm` / `decrypt_cfm` — такая же, как у `CTR` (§5): генерация `S`,
префикс, `split_at(BLOCK_SIZE)`, только с флагом `encrypt: true/false`.

Свойства для отчёта: длина сохраняется; зашифрование строго последовательное,
расшифрование распараллеливаемо; ошибка в блоке `Yᵢ` портит соответствующие биты
`Xᵢ` **и весь блок `X_{i+1}` целиком**, дальше поток восстанавливается —
самосинхронизация через один блок. Это главное отличие от `CTR`.

## 7. Имитовставка и хэш (п. 6.6, 6.9)

### `belt-mac`, п. 6.6

```
r ← F(0¹²⁸),  s ← 0¹²⁸
для i = 1..n-1:  s ← F(s ⊕ Xᵢ)
если |Xₙ| = 128:  s ← F(s ⊕ Xₙ ⊕ Ψ1(r))
иначе:            s ← F(s ⊕ (Xₙ ‖ 0x80 ‖ 0…0) ⊕ Ψ2(r))
имитовставка ← Left_64(s)          // 64 бита
```

где по 32-битным словам `u = u₁‖u₂‖u₃‖u₄`:

```
Ψ1(u) = u₂ ‖ u₃ ‖ u₄ ‖ (u₁ ⊕ u₂)
Ψ2(u) = (u₁ ⊕ u₄) ‖ u₁ ‖ u₂ ‖ u₃
```

Дополнение `Xₙ ‖ 1 ‖ 0…0` на байтовых данных — это добавленный байт `0x80` и
нули до 16 байт; пустое сообщение — тоже такой блок, так что имитовставка у него
есть (в отличие от ГОСТа, где `compute_mac` возвращает `None`).

`Left_64` — первые 8 байт состояния. Тесты ждут их упакованными так, что первый
байт — старший разряд `u64` (тогда печать совпадает с hex из стандарта), а
укорочение до `mac_bits` — это первые биты, не младшие. Собрать иначе можно,
но тогда придётся поменять ожидания в тестах.

### `belt-hash`, п. 6.9

Ключа нет, выход 256 бит, сообщение режется на блоки по 32 байта, последний
дополняется нулями. По 128-битным частям `u = u₁‖u₂‖u₃‖u₄`:

```
σ1(u) = F_{u₁‖u₂}(u₃ ⊕ u₄) ⊕ u₃ ⊕ u₄                      // 128 бит
σ2(u) = (F_{θ1}(u₁) ⊕ u₁) ‖ (F_{θ2}(u₂) ⊕ u₂)             // 256 бит
        θ1 = σ1(u) ‖ u₄,   θ2 = (σ1(u) ⊕ 1¹²⁸) ‖ u₃
```

то есть блок сообщения работает *ключом*, а не открытым текстом. Сам алгоритм:

```
s ← 0¹²⁸
h ← B194BAC8 0A08F53B 366D008E 584A5DE4 8504FA9D 1BB6C7AC 252E72C2 02FDCE0D
для i = 1..n:
    s ← s ⊕ σ1(Xᵢ ‖ h)
    h ← σ2(Xᵢ ‖ h)
хэш ← σ2(⟨|X|⟩₁₂₈ ‖ s ‖ h)
```

`⟨|X|⟩₁₂₈` — длина **исходного** сообщения в битах, поэтому нулевое дополнение
не склеивает `hash(X)` и `hash(X‖0)`.

Под `MacSpec` хэш не подходит (там ключ, `u64` и усечение по битам), поэтому в
CLI для него отдельный хук: `CipherApp::digest: Option<DigestSpec>` —
`fn(Vec<u8>) -> Vec<u8>`, без ключа и без фиксированной длины. Пункт меню уже
заведён и зовёт `BelT::hash`.

Все значения — байтовые строки в hex, пробелы для читаемости. `K` вводится в CLI

## 9. Как проверять

Векторы приложения А — байтовые строки, а публичные `encrypt_*` / `decrypt_*`
сами генерируют `S` и добавляют её префиксом, поэтому KAT идут мимо CLI и мимо
обвязки: вызывается внутренняя функция режима с фиксированной `S`. Тесты лежат
в `#[cfg(test)] mod tests` внутри `bel_t.rs` (приватные `encrypt_block`,
`apply_cbc` и прочее оттуда видны), гоняются через `cargo test -p lab2`.

Сигнатуры, на которые тесты уже написаны:

```rust
fn apply_cbc(bytes: &[u8], key: &Key<8>, sync: u128, encrypt: bool) -> Vec<u8>
fn apply_ctr(bytes: &[u8], key: &Key<8>, sync: u128) -> Vec<u8>
fn apply_cfm(bytes: &[u8], key: &Key<8>, sync: u128, encrypt: bool) -> Vec<u8>
pub fn compute_mac(message: Vec<u8>, key: &Key<8>, mac_bits: usize) -> Option<u64>
pub fn hash(message: Vec<u8>) -> Vec<u8>
```

Поменять их можно, тесты подстроятся; сейчас всё, кроме `apply_cbc`, — заглушки
`todo!()`, и 14 тестов падают именно на них. Зелёные — блочное преобразование,
ECB и CBC.

Что проверяется, кроме KAT:

1. **Round-trip.** Для `CTR` и `CFM` — все длины 0..80 байт, для `CBC` — от 16
   (кража шифртекста). Заодно проверяется `|Y| = 16 + |X|`.
2. **Размножение ошибки.** Портится один байт блока `Y₂`: в `CTR` обязан
   испортиться ровно один байт открытого текста, в `CFM` — этот байт и весь
   следующий блок, в `CBC` — весь блок `X₂` и один байт `X₃`. Это главное
   отличие режимов друг от друга, и именно оно ловит перепутанную обратную
   связь.
3. **Разные `S`** дают разный шифртекст для одного и того же открытого текста.
4. **Длина в хэше.** `hash(X) ≠ hash(X‖0)` — нулевое дополнение не должно
   склеивать сообщения разной длины.

Обратный порядок: сначала А.1/А.2 (блок), потом режимы. Если ключ или векторы
введены с опечаткой, А.1/А.2 падают первыми, и не приходится искать ошибку в
режиме, которого в ней нет.

## 12. Грабли

Коротко, что уже ломалось — чтобы не ловить это второй раз в `CTR`, `CFM`,
`belt-mac` и `belt-hash`.

1. **Потерянный последний блок в CBC** (§4). Цикл, который придерживает блок
   для кражи шифртекста, обязан придерживать его только при неполном хвосте.
   Round-trip такую ошибку не видит — расшифрование теряет блок симметрично,
   ловится только KAT на длине, кратной 16.
2. **Опечатка в ключе выглядит как ошибка в режиме.** `K2` был введён как
   `…E5D14011…` вместо `…E5D14101…`, и мимо шли все векторы на `K2` сразу.
   Проверять А.1/А.2 первыми: они падают на неверном ключе и не падают на
   неверном режиме.
3. **`full - 1` на коротком входе.** В ECB и CBC при `|X| < 16` это
   переполнение `usize`, а не «ноль блоков». Отсюда `assert!` в обоих
   `apply_*` и проверки `at_least` в `main.rs`.
4. **Проверка, которая ничего не проверяет.** У старой `check_ecb_padding` в
   `common` первой строкой стоял `return Ok(())`, так что весь разбор паддинга
   был мёртвым кодом. Проверки лучше держать рядом с режимом, который их
   формулирует, — теперь так и сделано (§3).
5. **Порядок байт в `Left_r`** (§1) — первые байты строки это младшие биты
   `u128`, а не старшие. Та же ловушка в `Left_64` у `belt-mac` (§7).
6. **Формулы из PDF не извлекаются** — только скелет из скобок и номеров
   шагов. Восстанавливать операции по контрольным примерам, а не по
   `pdftotext`.
